# Authority handoffs and changed prerequisites

Use this when a continuing goal is waiting on a credential correction, approval, ownership transfer, or missing historical invocation evidence. The project's native rules remain authoritative.

1. **Recover evidence locally when authorized.** Ask for an exact non-secret identifier and likely directory only if they cannot be inferred. Search the project ledger and native receipts first. If the user authorizes searching Codex session history, run `python scripts/afk_session_evidence.py --root <authorized-session-dir> --id <exact-RunId>`. The tool emits file, line, time, role and tool metadata, never message content or arguments. Inspect selected records only when needed, with secret-safe output. A prompt mentioning a RunId is not an invocation; a task scheduler reservation is not a project reservation. Correlate native entry and terminal evidence before deciding anything was entered or charged.
2. **Make the handoff reviewable.** For each relevant attempt, record expected evidence, actual observation, stable causal fingerprint, entry boundary, retry eligibility and next external prerequisite through supported AFK state/event APIs. Preserve old failures and allowance. A credential store `PASS`, changed mtime, or user report of secure entry is a material lead, not authenticated guest proof. An owner statement can establish that they used a known-correct secret without disclosing it; the project's admitted authentication check establishes whether it works.
3. **Use only the owner's approved channel.** Run a project's secure initializer only in the authorized principal and session, with interactive secret entry or an already approved protected store. Never request or transport plaintext, guess a secret, create an account, change policy, or auto-submit approval. If the user already completed the secure step, do not ask them to repeat it to gather more metadata.
4. **Separate admission from verification.** Before one live check, verify current candidate/target identity, operator ownership, native reservation/operation scope, deadline, host safety, cleanup owner and remaining allowance. A diagnostic that mutates a VM or remote system needs its own admission even when a later proof depends on diagnostic success. A missing reservation or ambiguous historical charge stops the live check; do not backdate, hand-edit, refund or infer permission from a skill, AFK state or model turn. Prepare a concrete prospective reconciliation and ask the actual owner only for the decision native evidence cannot supply.
5. **Resume automatically when gates are real.** After admission and a material changed condition, perform one supported verification, capture the original result and exact cleanup, then reconcile native state. If it still fails with the same credential or permission fingerprint, stop and tell the owner the precise observed failure. If it passes, continue the existing goal without a routine confirmation prompt. Keep the final acceptance oracle unchanged.

AFK can automate evidence retrieval, secure-store use already authorized by the project, native checks, and follow-through. It cannot supply an unknown password or become the native campaign owner. A project-specific skill or supported native entrypoint defines the executable details.
