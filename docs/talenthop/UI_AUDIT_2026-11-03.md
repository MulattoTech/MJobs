It followed visible navigation, footer links, tabs, dialogs and recommendation links. The user explicitly authorized private-session review and necessary audit writes. The sole persistence probe saved one job and removed that bookmark after verifying the tracker. ## Search and discovery

A job-title query returned live results with card/focus view controls. Focus view exposed the selected description, employer identity, compensation when available, an original-posting control and resume-analysis entry points. Some cards grouped related roles or locations with previous/next controls. Group navigation and full pagination were not exhaustively exercised.

The All Filters dialog exposed remote/hybrid/on-site choices, office allowance, travel allowance and level, work schedules, employment types, experience levels, salary unit and minimum, salary-required, education, posted age, quick/direct apply and visa sponsorship. This establishes the controls' presence. It does not establish the correctness of every combination.

A remote search was exercised, followed by an hourly minimum of 30. Entering the positive minimum automatically enabled salary-required. Applying the filters produced removable chips and URL criteria for remote, hourly frequency, minimum and salary-required. After settling, sampled visible cards carried hourly ranges. Clearing the filters returned to the broader search.

Search help advertises uppercase AND and OR. This audit did not establish the parser's truth table. A hyphenated probe containing ordinary words still returned word-related matches; therefore it was not treated as an exact-match empty-state test. A second random alphabetic query returned zero jobs, a clear empty message and an unselected detail state.

Search sometimes displayed the prior result count/detail while the new request was visibly loading, then settled. No timing percentile, HTTP latency, race-condition proof or cache conclusion is inferred from that observation.

**MJobs decision:** reuse its existing normalized job/search model. The inspected main search API and UI expose annual USD bounds even though salary parsing and saved criteria already know HOUR/YEAR. [#918](https://github.com/MulattoTech/MJobs/issues/918) specifies the integrated hourly/annual controls, compatible-unit filtering, unknown-salary policy and round-trip tests. Preserve original amounts and source certainty; do not silently annualize hourly pay.

## Recommendations and explanations

The dashboard rendered existing resume-backed recommendations. Cards exposed compensation, age, employer, remote labeling, match percentages, matched skills, save/pass/apply actions and similar-role links. Existing recommendations were read; no new model run was requested.

Opening a match score produced a skills-analysis dialog. It separated profile fit from keyword matching and represented one unassessed component as unassessed rather than zero. Skills were grouped into full and partial matches. Job detail also displayed existing full/partial/missing counts.

These observations establish an explanation UI, not the correctness of scores, the definition of its percentages, the ranking algorithm or a probability of employment. Query parameter names are not evidence of backend implementation.

Autofill on the dashboard was explicitly marked incoming/unavailable. It must not be counted as an operating reference workflow.

**MJobs decision:** retain its explanation and fact-trace modules. Unknown evidence must stay distinct from low fit. Suggested wording, scores or tailoring must not invent credentials, experience or skills. Existing original acceptance and future parity tests remain independent.

## Saved jobs, recent views and application status

A previously unsaved result was temporarily saved. After navigating to Job Tracker, it appeared in the list with an explicit saved/not-applied status; Applied stayed at zero. Saved-only filtering was exercised. The same job was then unsaved, the filter disabled, and the tracker returned to its original empty state, including after reload.

The tracker provides All, Applied, Pending, Accepted Offer and Rejected tabs. Those application-state transitions were not exercised by creating fictitious employer submissions.

Recently Viewed is a distinct list. Saved-only filtering became disabled there and explained that it does not apply to that server-paged view. The audit did not publish the account's historical job records. A subsequent original-posting handoff also left Applied at zero.

One visible labeling inconsistency is actionable: the footer described the single saved-only row as an application, while the row correctly distinguished saved from applied. MJobs should maintain separate bookmark, view, handoff and confirmed-submission counts.

**MJobs decision:** its existing job dispositions and application tracking provide partial overlap. Search execution history is not job-view history. [#919](https://github.com/MulattoTech/MJobs/issues/919) specifies a bounded per-profile recent-view list with isolation, deterministic order, stale-job handling and no application-state mutation.

## Resume and preference workflows

The base-resume area listed existing versions with timestamps, primary-selection controls, viewing, deletion and match-to-job entry points. An existing viewer opened and was closed. No private document contents were retained in this evidence package.

The upload dialog requires a name and file and advertises PDF, DOC, DOCX, RTF and ODT with a 10 MB limit. The dialog was cancelled. The audit does not attest MIME validation, parsing fidelity, malware controls, error handling, OCR or the actual acceptance of each format.

The job-optimized list was empty in the inspected account. Creation requires a base resume, company, title, application URL and job description. The form states that a cover letter accompanies optimization. The required-field/disabled-action state was observed, but generation, before/after comparison, factual validation, export and generated-version persistence were not run.

Job Preferences includes role and target-location selection, yearly/hourly minimum salary, benefit choices, work arrangement, experience, education and work schedule. Fields were inspected without saving changed preferences. The `job-alerts` route name alone was not treated as proof of notification behavior.

**MJobs decision:** reuse its resume library, workspace, reviewed rewrites, provenance and output modules. Keep base documents separate from job-specific derivatives. Test format support and generation outcomes with synthetic fixtures and authorized providers; reference advertising is not acceptance evidence.

## Account, alerts, trust and support

Account Info exposes a profile editor with contact/location/professional-link fields and a password-change entry point. The edit dialog was cancelled; no credential or profile change occurred.

Notifications has email/SMS switches for platform news and job-match alerts and links back to job preferences. No preference toggle, delivery, unsubscribe, scheduling, retry or deduplication outcome was exercised. Subscription exposes current-plan, payment-method and billing-history sections. Upgrade shows plans and renewal conditions. No purchase or subscription change was initiated.

Two public statements conflict: the upgrade screen advertises a 14-day money-back guarantee, while the separate refund policy gives a 7-day request window. This report records the content discrepancy; it does not infer which condition is legally controlling or whether a refund would succeed.

The privacy page describes access, correction, deletion and portability rights. No self-service export/delete control was found in the inspected account screens, and no request was submitted. This remains a policy claim with an untested operational outcome.

Job-detail reporting offers reasons for scams, recruiters, misleading information, expired jobs, duplicates, spam and other issues. The form was cancelled. Freshness/verification labels were observed, but their underlying review process, actual authenticity and report handling remain unverified.

**MJobs decision:** preserve provenance and uncertain source status. Add only supported moderation/feedback behavior; do not imply every listing is verified. Existing account/export work is partial overlap. A reference subscription business model does not itself require adding billing to MJobs.
